# План урока 3: миграция с direct на topic + расширение сценариев (users/orders/analytics)

## Контекст
Сейчас в проекте уже реализован первый рабочий сценарий через `direct`: уведомления после регистрации и после подтверждения email. Следующий этап курса — показать, как перейти к событийной модели `topic`, чтобы одно событие можно было безопасно и гибко маршрутизировать в несколько независимых очередей. Это даст студентам понимание масштабирования без переделки producer-кода при добавлении новых consumers.

## Цель этапа
1. Перевести маршрутизацию RabbitMQ с `direct` на `topic`.
2. Сохранить существующие сценарии users-notifications.
3. Добавить сценарии после оплаты заказа и асинхронную аналитику в админку.
4. Сформировать устойчивый паттерн: `domain event -> routing key -> несколько очередей`.

## Почему нужна миграция на topic
`Direct` хорошо подходит для первого знакомства, но быстро становится неудобным при росте количества сценариев. В `topic` мы можем использовать ключи вида `users.registered`, `orders.paid`, `orders.*`, и это позволяет добавлять новых подписчиков без изменения существующего producer. Для учебного процесса это важно: студенты видят, что архитектура сообщений может расширяться эволюционно, а не через постоянный рефакторинг ядра.

## Событийная модель, которую вводим
1. `users.registered` — пользователь зарегистрирован.
2. `users.verified` — пользователь подтвердил email.
3. `orders.paid` — заказ оплачен.
4. `orders.created` / `orders.canceled` — события для аналитики и отчетов.

Эти ключи нужно сделать единообразными и стабильными, потому что они становятся API между producer и consumer. Мы закладываем стиль `domain.action`, чтобы студентам было проще читать и поддерживать маршрутизацию.

## План реализации в коде

### Шаг 1. Подготовка topic-конфига RabbitMQ
1. Обновить `.env.example`:
   - `RABBITMQ_EXCHANGE_NAME=app.events`
   - `RABBITMQ_EXCHANGE_TYPE=topic`
2. Оставить существующие параметры durable/declare, чтобы не терять устойчивость очередей после рестартов.

Аргументация: `app.events` как общее имя exchange упрощает объяснение модели “единая шина событий приложения”. Для обучения это удобнее, чем заводить множество exchange на старте.

### Шаг 2. Ввести общий publisher-слой (тонкая обертка)
1. Добавить сервис-публикатор, например `App\Service\Messaging\EventPublisher`.
2. В нем централизовать отправку сообщений с указанием routing key и payload.
3. Producer-код (регистрация/оплата) должен использовать этот сервис, а не scattering dispatch по контроллерам.

Аргументация: централизация публикации уменьшает дубли и делает урок чище. Студенты видят единый вход для событий и проще понимают, где управляется формат сообщений.

### Шаг 3. Миграция users-сценариев на topic
1. Для регистрации публиковать `users.registered`.
2. Для подтверждения email публиковать `users.verified`.
3. Сохранить отдельные consumer-очереди:
   - `users.notifications.verify`
   - `users.notifications.welcome`
4. Привязки (binding):
   - `users.registered` -> `users.notifications.verify`
   - `users.verified` -> `users.notifications.welcome`

Аргументация: логика, знакомая студентам из direct-урока, остается прежней по смыслу, но переходит на более гибкий транспорт. Это мягкая миграция без когнитивного шока.

### Шаг 4. Добавить producer после оплаты заказа
1. В точке подтверждения оплаты заказа (после успешной смены статуса на paid) публиковать `orders.paid`.
2. Payload: `order_id`, `user_id`, `total`, `paid_at` (минимально необходимый набор).

Аргументация: это реальный бизнес-кейс с высокой ценностью. Студенты видят, что критичный путь оплаты остается в приложении, а побочные операции уходят в очередь.

### Шаг 5. Добавить consumer для уведомлений по оплаченному заказу
1. Очередь `orders.notifications`.
2. Binding `orders.paid` -> `orders.notifications`.
3. Job-обработчик: отправка чека/уведомления клиенту и/или менеджеру.

Аргументация: отдельная очередь изолирует канал коммуникаций от остального фона. При проблемах почты аналитика и другие задачи не блокируются.

### Шаг 6. Добавить consumer для аналитики админки
1. Очередь `orders.analytics`.
2. Binding `orders.*` -> `orders.analytics`.
3. Job-обработчик: обновление агрегатов (сумма продаж, количество заказов, отмены и т.п.).

Аргументация: wildcard-подписка идеально демонстрирует силу `topic`. Один consumer может реагировать на множество связанных событий без изменений producer.

### Шаг 7. Настроить retry и устойчивость
1. Для notification jobs: умеренный `tries` и `backoff`.
2. Для analytics jobs: больше попыток и более длинный backoff.
3. Добавить обработку `failed()` с логированием контекста (`event_key`, `entity_id`).

Аргументация: разные типы задач имеют разные SLA, и студенты должны видеть это на практике. Нельзя одинаково настраивать повторные попытки для всех очередей.

### Шаг 8. Подготовить запуск worker-ов по ролям
1. Worker 1: `users.notifications.verify,users.notifications.welcome`.
2. Worker 2: `orders.notifications`.
3. Worker 3: `orders.analytics`.

Аргументация: разделение worker-ов показывает горизонтальное масштабирование и изоляцию нагрузки. Это важный production-навык, который легко продемонстрировать даже локально.

## План урока (структура подачи студентам)
1. Короткое напоминание direct-сценария (что уже есть).
2. Объяснение проблемы масштабирования direct.
3. Переход на topic (конфиг + naming routing keys).
4. Реализация users-событий на topic.
5. Реализация orders.paid для уведомлений.
6. Реализация orders.* для аналитики.
7. Демо отказов: ломаем один consumer, проверяем, что остальные продолжают работать.
8. Закрепление: мини-задание на добавление нового event key.

## Проверка готовности после внедрения
1. `users.registered` приводит к задаче в `users.notifications.verify`.
2. `users.verified` приводит к задаче в `users.notifications.welcome`.
3. `orders.paid` приводит к задаче в `orders.notifications` и одновременно в `orders.analytics` (через wildcard binding).
4. При временной ошибке в consumer срабатывают retry по заданной политике.
5. В RabbitMQ UI видны exchange `app.events`, bindings и активность очередей.

## Риски и как их закрываем
1. Риск дублирования сообщений при retry.
   - Решение: делать обработчики идемпотентными (проверка “уже отправляли/уже считали”).
2. Риск перегрузки одной общей очереди.
   - Решение: разделение на очереди по ответственности.
3. Риск “тихих” ошибок в фоне.
   - Решение: обязательное логирование и просмотр failed jobs.

## Критерий завершения этапа
Этап считается завершенным, когда все три бизнес-сценария (регистрация, оплата, аналитика) работают через `topic`-маршрутизацию, а студенты могут объяснить, где producer, где consumer, как устроены bindings и почему разные очереди обслуживаются разными worker-процессами.
